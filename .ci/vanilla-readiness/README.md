# Измерение совместимости с vanilla 26.3

`python3 .ci/vanilla_readiness.py --verify-ci --markdown VANILLA-READINESS-MEASUREMENT-26.3-RU.md --json readiness.json`

Это не старая субъективная оценка. Считаются результаты по явно названным сценариям, но **общий процент vanilla-ядра не вычисляется**: полный непересекающийся перечень серверного поведения не установлен. Неизвестные сценарии остаются неизвестными, а не успехом или ошибкой. Тесты самóй считалки: `python3 -m unittest discover -s .ci -p 'test_vanilla_readiness.py' -v`.

## Текущие независимые срезы

* `smoke-inventory.json`: 38 поимённых условий существующего теста live-server, зафиксированного на `d8810e6`. Для этого конкретного набора есть парные серверные результаты `smoke-d8810e6.json`, восстановленные из комментариев к коммиту. Workflow [45082985134](https://github.com/Greston897/SteelMC/actions/runs/45082985134) завершился success, включая задания обоих серверов и сравнения. Каждый результат — выполнение одного и того же условия, **не** полное сравнение всего состояния и не доказательство целой механики. Работа без игровых клиентов. Результат исторический, если рабочее дерево грязное или HEAD отличается.
* `datapack-live-ba05896.json`: результаты [парного запуска 45090490433](https://github.com/Greston897/SteelMC/actions/runs/45090490433) на двух реальных серверах без клиентов. Vanilla прошёл 5/5 сценариев; Steel — 2 прошли, 1 не прошёл, 2 заблокированы. Общий CI намеренно имеет `failure`: проверка disable действительно выявила, что функция продолжает работать. JSON содержит отдельные результаты и хэши стенда/сравнения; при изменении стенда старое доказательство отклоняется и требует явного обновления. Это не проверка recipes, loot, client sync, ZIP или overlays.
* `.ci/manual_mechanics_cases.tsv`: 107 ручных сценариев в нескольких подсистемах. До загрузки парного результата все неизвестны. Сценарии могут пересекаться и не составляют полного перечня механик.
* `trigger-inventory-26.3.json`: 58 ID из `CriteriaTriggers.java` vanilla. Это **учёт источников**, а не 58 тестов; положение в gate не доказывает полную работоспособность. Чтобы заново сверить источник, передайте `--vanilla-source /путь/к/CriteriaTriggers.java`; файл должен совпасть по SHA-256 с зафиксированным исходником, созданным [Actions](https://github.com/Greston897/SteelMC/actions/runs/44926675892). Без файла используется сохранённая инвентаризация, и вывод явно сообщает об этом.

Сценарии разных наборов нельзя складывать или распространять их процент на всё ядро. `0/107` проверенных — это не утверждение, что все 107 сценариев сломаны; без результатов все они **unknown**. `38/38` — не 100% общей готовности. В коде `global_readiness_percent` всегда `null`.

## Новый парный прогон

1. Запустите один и тот же закреплённый сценарный набор на официальном сервере 26.3 и Steel, получите два полных `results.json` из артефактов/комментариев одного Actions run. Запись содержит `engine` (`steel` или `vanilla-26.3`) и `results` с уникальными `name`, `passed` (boolean). Ошибки/отсутствующие результаты нельзя подменять успехом.
2. Импортируйте проверенные файлы и метаданные завершённого Actions run:

```sh
python3 .ci/record_vanilla_readiness.py \
  --inventory smoke --run НОМЕР_ЗАПУСКА \
  --steel /путь/steel/results.json --vanilla /путь/vanilla/results.json \
  --output /путь/evidence.json
python3 .ci/vanilla_readiness.py --verify-ci --smoke-evidence /путь/evidence.json \
  --markdown VANILLA-READINESS-MEASUREMENT-26.3-RU.md --json readiness.json
```

Для 107 ручных сценариев используется `--inventory manual` и затем `--manual-evidence /путь/evidence.json`; результаты должны использовать именно ID из TSV. Вводные условия и ожидаемые результаты для всех 107 кейсов задаёт TSV. Настоящий парный прогон этих кейсов пока не реализован, подменять его локальными фиктивными JSON нельзя.

Импортёр проверяет SHA и состояние run через `gh`, формат и точное соответствие ID инвентарю. Пропуски остаются unknown; неизвестные/дублированные ID, другие версии инвентаря и неверные типы отвергаются. SHA-256 полного файла инвентаря связывает результаты с той редакцией списка. Если изменились смысл или проверки сценариев, нужно создать новый фиксированный инвентарь и новый парный прогон, а не переписывать старые результаты.

**Важная граница доверия:** проверка метаданных run не удостоверяет, что произвольные локальные `results.json` действительно получены из этого run. Их происхождение нужно сверить с артефактами/опубликованными комментариями. Наличие двух `passed` означает только что два сервера независимо удовлетворили условию теста, а не что между ними сравнены все результаты. CI-метаданные проверяются по `--verify-ci`; при отсутствии сети или ошибки проверки отчёт этого не скрывает.

## Итоговые статусы

* `matched_assertions` — одноимённое условие прошло на обоих серверах.
* `steel_failed` — условие прошло на vanilla, но не прошло на Steel.
* `invalid_reference` — условие не прошло на vanilla, поэтому считать его расхождением нельзя.
* `unknown` — хотя бы один результат отсутствует.

Совпадение SHA и успех CI не позволяют объявить покрытой механику за пределами конкретного сценария. Для достоверного общего процента ещё необходимы полная декомпозиция vanilla-сервера на наблюдаемое поведение, согласованные веса, тесты всех границ и клиентской синхронизации, привязка их к текущему коммиту и проверенный источник каждого результата. Пока этого нет, единственного реального процента не существует.
